[playhold](https://github.com/ny4rl4th0t3p/playhold) v0.4.0 is out, a small release with one job: its two SDKs and
its sample game, Crazy Eights, now live in repositories of their own. Nothing changed for a player; a lot changed for
anyone who wants to build on it. And moving the code apart found a bug that had been in the design all along.

<!-- more -->

## Why split

Until now, the TypeScript SDK, the Go SDK and the sample game all lived inside playhold's repository. A game used them
from a clone, with a `file:` path into it. That's fine for the author and useless for anyone else: the next step is a
tutorial, and a tutorial needs a stranger to install the SDKs with one command.

```sh
npm install git+https://github.com/ny4rl4th0t3p/playhold-sdk-ts.git#v0.4.0
go get github.com/ny4rl4th0t3p/playhold-sdk-go@v0.4.0
```

The sample game moved for a different reason: inside playhold, it could reach things no other game can, such as
playhold's internal packages. In [playhold-crazy-eights](https://github.com/ny4rl4th0t3p/playhold-crazy-eights) it
builds on tagged releases only, as a stranger's game would. That made one of its tests change: it used to check a saved
game by decoding playhold's internal storage format, which no game should depend on. It now restarts the server on the
same store and checks the player gets their hand back, which is what the game actually cares about.

## One direction

Three repositories that depend on each other can easily become a release that waits on itself. The rule that keeps it
simple: dependencies go one way, playhold → SDKs → game, and never back.

- Each SDK pins one playhold tag, for two things: the wire code it's built against, and the small game server its tests
  run against, which sits in a module of its own so the SDK itself never depends on playhold.
- Versions are linked by their minor number: an SDK `v0.4.y` works with any playhold `v0.4.*`, so the patch number
  carries each side's own fixes, and anyone can see which versions go together.
- Every release goes in the same order: playhold is tagged, then each SDK moves to it and is tagged, then the game, then
  playhold's documentation moves to the game's tag.

A first idea, a public test server inside playhold that each SDK's tests would download and run, didn't survive a second
look: playhold's releases would have become a moving part of every SDK's tests. Each SDK keeping a few dozen lines of
test server of its own costs far less than that tangle.

## The docs still show tested code

The documentation's examples are imported from the game's real, tested files, never typed into a page. With the game in
another repository, the documentation build now checks it out at a pinned tag first and imports from there, so a missing
example still fails the build, and the pages show the code of a released game.

## What's next

The tutorial: building a small game from nothing, on the SDKs as they install today.
