[playhold](https://github.com/ny4rl4th0t3p/playhold) is a self-hosted game backend in Go, built as a hobby: each game
runs in an authoritative room, and game logic lives in modules that never import each other. v0.3.0 is out. It's the
release about putting a server in front of strangers: TLS and safe defaults, rate limits, refusing new games while
overloaded, and ways to find out what crashed it. This post starts a journal of what each release teaches; the
[documentation](https://ny4rl4th0t3p.github.io/playhold/) has the details.

## A game that survives

The test every release has passed since v0.2 plays one game of the sample, Crazy Eights, with two bot players, and
interrupts the server three times mid-game: a clean restart, a `kill -9`, and a deploy of a build that saves games in a
new format, so the saved game has to be migrated first. It passes only if the game ends with a winner both players
agree on, and nobody lost their seat or a card.

For v0.3.0, each player reconnected 3 times and was back in the game within 0.2 to 1.25 seconds, with no move lost.
The test is `done-test.sh` in the
[sample](https://github.com/ny4rl4th0t3p/playhold/tree/main/examples/cards#see-a-game-survive).

## What saving costs, and two fixes that didn't work

Rooms save a snapshot after every change, so a crash loses at most the moves not yet written. v0.2 measured what that
costs: the sample at 3,000 moves a second over 1,000 connections, the game server limited to one CPU core, 6 runs with
saving off and 6 on.

| Moves answered within | Saving off   | Saving on    |
|-----------------------|--------------|--------------|
| p50                   | 582–587 µs   | 614–621 µs   |
| p99                   | 2.85–3.23 ms | 5.86–6.63 ms |

The median barely moved while p99 doubled: saving made some moves slow, not every move. Profiles came before any fix.
Saving took the game server from about 25% to about 36% of its one core, and on a single core the time goroutines wait
to run grows faster than the load. The garbage collector was a minor part: `GOGC=400` cut p99 by about 1 ms with saving
off and on alike, and left the gap.

The obvious fixes were cheaper saves: one SQL statement per batch instead of one per room, and snapshots encoded into
reused buffers. They cut allocations by 5 to 10%, but not CPU, and p99 with saving on got worse, compared on the same
day: 6.36–6.94 ms before, 7.13–7.67 ms with the buffers, 7.58–8.99 ms with both. Both were dropped.

Saving less often worked. With `SnapshotInterval` at 1 second, a busy room saves at most once a second; rooms written
fell from about 3,130 to about 650 a second, and p99 with saving on to 4.55–5.23 ms, against 3.17–3.70 ms off. The
price is explicit: a crash can lose up to one interval of moves. The default stays 0, saving after every change,
because a turn-based game makes far fewer moves: at 200 moves a second, the check below measured saving adding about
0.15 ms to p99.

The lesson worth keeping: measure the cause first. Both cheaper saves were reasonable guesses, and both made worse the
number they were meant to fix.

## Crashes: a journal and a breaker

A Go server can't recover from everything: a goroutine stuck in a loop can't be stopped, and some crashes take the
whole process down. Two pieces help find and contain those.

The **crash journal** keeps the last turns in a fixed-size file used as a ring: for each turn, the room, the player,
the message, and how the turn ended. After a crash, the turns that were running are the first suspects, and their
messages are there to reproduce them. It's off by default. One load run with it on and one with it off, at 3,000 moves
a second, showed no cost a single run can see: p99 3.7 against 3.9 ms with saving off, 7.8 against 9.7 ms with saving
on.

The **breaker** turns off a message that keeps hurting the server. It counts incidents: turns that hurt the whole
server, either by crashing the process or by still running 30 seconds after the watchdog gave up on them. Three
incidents from the same message within 10 minutes turn that message off for an hour, and clients sending it get an
explicit error. A room involved in 2 incidents isn't restored.

Panics don't count. A panicking room is restored and the server carries on, and a few panics among thousands of
messages are too little evidence to turn a message off for everyone.

The thresholds weren't measured; they're a judgment. Incidents are saved, so the breaker remembers them across the
restarts they cause.

## 1,000 players over TLS

v0.3's release check plays 500 games, 1,000 players each moving every 2 to 8 seconds, over TLS. The game server runs in
a container limited to 1 CPU and 1 GB, with PostgreSQL and the bot in their own containers on the same 4-core virtual
machine. It gates on what players notice rather than on server micro-numbers: moves answered within 100 ms at p99, no
lost games, explicit refusals when full, stable memory, and saving that keeps up.

| Set                                       | Result                                                                    |
|-------------------------------------------|---------------------------------------------------------------------------|
| Saving off and on, 3 runs each            | p99 1.74–1.78 ms off, 1.91–1.94 ms on, no failures                        |
| 12 hours, saving on                       | p99 1.67 ms, no failures, memory 139.5–140.4 MiB from minute 2 to the end |
| Server restarted 2 minutes in             | All 1,000 players back in their games, the slowest after 1.4 s, none lost |
| 2,000 players, room for 600 games         | Every refused game told so; p99 4.22 ms for the players who got in        |

The latencies sit far inside the 100 ms gate; the check is mostly about everything else: hours without drift, a
restart under load, and what happens past capacity. The numbers come from one machine and aren't a benchmark; the
[measurements page](https://ny4rl4th0t3p.github.io/playhold/measurements.html) says how they were taken.

## Working with an agent

playhold is written with an AI coding agent. What makes that work: a written plan approved before any code,
measurements before fixes, and every line reviewed before a commit. It still makes mistakes. In this release's check,
a script ran one set at half the load it should have; reading the results caught it, and the set was run again.

## What's next

Building your own game on playhold is still harder than it should be: the SDKs aren't published as packages yet. Next
come the SDKs in their own repositories, a real deploy on a VPS with the same survival test, and then Crazy Eights on
itch.io.
